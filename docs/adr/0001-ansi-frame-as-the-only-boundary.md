# コアと表示の境界を ANSI フレーム文字列にする

同じゲームをターミナル（CLI バイナリ）とブラウザ（`GOOS=js GOARCH=wasm`）の両方で動かすにあたり、
コアが外へ何を渡すかを決める必要があった。**コアは ANSI エスケープを含んだ描画済み文字列
（→ CONTEXT.md「フレーム」）を吐き、CLI はそれを標準出力へ、ブラウザは xterm.js へ流し込む**ことにした。
xterm.js は本物の端末エミュレータなので、ブラウザに出ているのは端末出力そのものになる。

## 考えた代替案

コアが盤面の状態（セル配列など）だけを返し、ANSI レンダラと DOM/Canvas レンダラを別々に書く案。
こちらの方が表示の自由度は高いが、**レンダラを 2 つ保守することになる**。
このプロジェクトの主目的は Go の学習であってブラウザ描画の作り込みではないため、
レンダラを 1 つに畳んでゲームロジックに時間を使う方を選んだ。

## 引き受けた帰結

- ブラウザ側の見た目は「文字グリッド」に固定される。滑らかなアニメーションや
  ピクセル単位の演出はやらない。やりたくなったらこの決定ごと覆すことになる。
- 逆に、**この境界を跨ぐものは文字列だけ**なので、コアは `syscall/js` にも
  端末にも一切依存しない。コアのテストは文字列の比較だけで書ける。

## この約束が及ぶ範囲（M2 で明確にした）

「唯一の境界」は**端末に描かれる絵**についての約束である。端末の外側——ブラウザ版で言えば
ページの読み込み表示、操作説明、ゲームオーバー後の案内——はこの約束の対象ではない。

ブラウザ版のドライバは、フレームのほかに次のものを Go から JS へ渡す（`cmd/tetro-wasm`）。

- **端末の桁数と行数**（`render.Size()`）。端末をフレームぴったりの大きさで作らせるため。
- **操作説明**（`input.KeyHelp()`）。キーの割り当てを持っている場所から出す。
- **ゲームが終わったという通知**。ページ下の案内を差し替えるため。
- **タッチボタンの一覧**（`input.Buttons()`、M3 で追加）。何個あり・何と書かれ・
  どちらの親指に置かれ・押しっぱなしで繰り返してよいか。操作説明と同じ理由で、
  キーの割り当てを持っている場所から出す。

いずれも「盤面をどう描くか」ではなく、**表示側の器をどう用意するか**である。これらを JS 側に
書くと、盤面の大きさやキーの割り当てを変えたときに片方だけ古くなり、しかも動き続けるので
誰も気づかない。境界を緩めているのではなく、**境界の外にあるものの出どころを 1 つに保っている**。

## 入口側の境界（M3 で明確にした）

出口の境界がフレームひとつであるのに対し、**入口の境界は「入力」（`game.Input`）ひとつ**である。
バイト列ではない。

M2 まではこの 2 つが見分けられなかった。キーが `ESC [ D` として届くので、
「入口の境界はバイト列」と書いても同じことを指していたためである。M3 でタッチボタンを
足したときに分かれた——ボタンにはバイト列という形が無い。ボタンのために JS 側で
`ESC [ D` を組み立てれば、入口は 1 本に見えるが、**「←は ESC [ D」というキーの綴りが
`internal/input` の外へ漏れる**。そのあと割り当てを変えて JS を直し忘れても、
ボタンは動き続ける——別のキーとして。

そこでブラウザ版のドライバは Go 側に入口を 2 つ持つ（`cmd/tetro-wasm`）。

- **`data(バイト列)`** — 端末から届いたキー。`input.Decoder` が読み替える。
- **`press(id)`** — タッチボタン。`input.Press` が読み替える。

入口は 2 つだが、**どちらも `game.Handle(input)` の 1 点に合流する**ので、
操作の解釈が二重になることはない。読み替えの表はどちらも `internal/input` の中にある。
